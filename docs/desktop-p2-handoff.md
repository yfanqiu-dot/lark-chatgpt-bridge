# P2 开发接续说明

更新：2026-09-24。**P2 已在 `p2/topic-projects` 分支启动开发；本文保留目标与 P1 交接基线，当前实施状态见 [P2 进展](desktop-p2-progress.md)。** P1 固定单群普通文本最小闭环已验收关闭；详见 [P1 最终验证记录](desktop-p1-validation.md)首节。

## 目标与边界

P2 将 P1 的“一个已登记群对应一个已有桌面对话”扩展为：用户明确提出新建话题时，在选定项目下创建新的原生 Codex 桌面对话，建立对应飞书群并加入用户与 QIU，持久绑定群、项目和对话；同群后续消息继续该对话。项目文件夹中保存可读的群/对话索引和会话记录。明确的新建请求才创建资源，普通追问不得触发创建。

本阶段验收：同一项目的两个新话题得到两个群、两条项目对话，消息、结果及停止操作互不串线；另一个项目的归属准确；相同创建请求重试不重复建群或对话；中途失败后能继续剩余步骤；项目内索引和记录可读、可更新。P3 才覆盖任意进程崩溃、长时稳定性和更多并发故障；P4 才考虑正式切换及旧 bridge 清理。

## 建议实施顺序

1. 先定义可持久化的 `chatId → projectId/projectRoot/threadId` 注册表、每群独立消息账本和项目可读索引；旧 P1 单群账本保持原样，设计明确的迁移与只读回退。
2. 核实本机当前 Codex 桌面/ App Server 的项目与任务创建能力，以及 QIU 机器人对创建群、加成员和读写群信息的实际权限。飞书读写遵守项目 `AGENTS.md` 的身份规则；若机器人写入受限，改用用户身份须获得该项操作的明确授权。
3. 把“新建话题”实现为可续办状态机：验证本人、目标项目和命名 → 记录操作与幂等键 → 创建并记录原生桌面对话 → 创建并记录飞书群 → 核验成员及机器人 → 激活绑定 → 告知新群入口。每一步先保存可恢复状态；失败不自动删除已建资源，重试复用其 ID。
4. 按群路由现有串行控制器、去重账本、审批与结果回传，并保持原群/原回复话题定位。新群创建与消息消费须协调唯一消费者，不能让旧 bridge 和新 bridge 同时争抢 QIU 事件。
5. 从真实原生对话历史生成项目内 Markdown 记录和群/对话索引，标注同步时间与不完整范围；导出不能代替桌面原生历史，也不能把跨项目资料写错目录。
6. 先做不触达飞书的状态机与迁移测试，再在授权测试范围内验证两个同项目话题、一个跨项目话题、重复请求、中途失败续办及记录更新。保存资源 ID、群消息回执、真实任务归属和恢复结果；不要复跑 P1 已通过的审批/三轮测试来充当 P2 证据。

## 已知边界

飞书 `post` 信封仅有输入适配单元测试，尚无本人真实 `post` 消息闭环；当前命令审批协议无独立 `decline` 决定；`/stop` 只停止模型轮次，已经启动的外部命令可能继续。这些不是 P1 最小闭环的通过项，P2 不能将它们记为已验收。旧桥继续承担日常消息消费；P2 开发不等于 P4 正式切换。
