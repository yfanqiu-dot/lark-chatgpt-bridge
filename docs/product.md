# 产品目标与开发边界

让飞书机器人把用户消息送到本机 Codex 桌面的真实项目对话，两端共享上下文。既有桌面通过飞书 CLI 查询/发消息的能力继续保留。

| 核心功能 | 用户体验 | 阶段 |
|---|---|---|
| 群与对话绑定 | 一个飞书群对应一个指定项目下的 Codex 对话 | P1 固定单群；P2 多群 |
| 发起和继续工作 | 本人在绑定群中 @机器人，排队处理并收到最终结果 | P1 |
| 两端接续 | 从飞书开始、桌面修改、飞书追问，沿用同一段历史 | P1 现场验收项 |
| 状态、追加、停止、审批 | 看清进度，控制本群任务，按具体操作确认权限 | P1 基础功能 |
| 新建话题 | 明确要求新话题时，创建新群、邀请用户/机器人，并创建项目对话 | P2 |
| 项目记录 | 按项目保存群与对话索引及可读记录，包含两端交流 | P2 |
| 日常运行 | 断线/重启/异常可恢复，升级有检查，正式切换可回退 | P3/P4 |

只有明确的新建话题请求才建群，普通回复串仍继续当前群的绑定对话。群成员身份不自动赋予本机执行/审批权限；首版只接受登记的所有者。只自动回传飞书发起轮次的结果，桌面新增交流进入共同历史。

技术路线是 **桌面与 bridge 共用一个本机 App Server**。各自启动独立后台、仅共享同一历史目录，不能解决同一对话的写入冲突。共享启动器、桌面后端、飞书接入、持久账本分工清楚；不直接修改 Codex 私有数据库，也不靠 UI 模拟输入。

P1 采用独立启动入口，复用原 bridge 的飞书 channel、应用消费锁和原子写文件工具；单群账本使用 JSON。多群、创建流程事务、数据库迁移在相应阶段处理，不向 P1 加入隐含部署依赖。

P1 验收必须包括真实测试群连续三轮、中间切到桌面修改再接续、重复消息不重复执行、状态/停止/审批可用和普通桌面恢复。测试通过和 P0 协议可行性都不等于现场验收通过，当前状态见 [验证记录](desktop-p1-validation.md)。

首版依赖这台电脑开机联网，不承诺关机后的云端代理执行。附件、多用户共同控制、完整桌面消息镜像不是 P1 前提。
