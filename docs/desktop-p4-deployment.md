# QIU Bridge 日常使用与运维

适用于 v0.10.0 的 Windows `new-only` / `stop-with-desktop` 部署。首次安装见[安装指南](../README.desktop.md)。这里描述正式会话模式，不沿用开发验收的短窗口或旧操作时间。

## 完整功能部署 v0.9.0

首次安装仍用单群验证基本收发。完整模式由部署清单中的 `"scope": "registered-topics"` 显式启用，接入入口群及注册表中全部已有话题群，并允许所有者在已配置项目中创建新话题。这里的“话题”是一条真实 Codex 对话及其独立飞书私有群。任意把机器人拉入的陌生群不会自动绑定对话，其他成员也不会获得所有者权限。

升级完整模式时，先保存现有配置及账本，停止消费者并核验清理。复制 `host.json`、`topics.json`、`deployment.json` 到新的配置目录，保留实际注册表、已有对话、消息账本及审批记录路径。不要对已有安装运行新装向导，也不要修改旧清单中已固定的配置文件。

在新的配置副本中：

- `topics.json` 删除 `enabledChatIds`，设置 `allowTopicCreation: true`。保留自己的 `entryChatId`、`existing`、所有者及项目清单。
- `host.json` 的 `topicProjects` 必须列出对应的真实项目 ID 和根目录；已有 `toolBindings`、程序版本与 SHA 重新核对后保留。
- `deployment.json` 增加 `scope: "registered-topics"`，将 `hostConfigFile`、`topicConfigFile` 指向新副本，将程序路径与完整工具目录指向本次验证的安装。保持原凭据服务引用。
- 对照原生历史处理每条 `uncertain`，保留原消息和核对证据。无法唯一证明归属或终态的任务继续暂停，不清账，不重新提交。

然后按[安装指南](../README.desktop.md#5-生成全新配置)中的 `prepare`、`verify`、`--service-prepare` 命令生成**新的** stage 和 service 目录。使用新的清单 SHA 启动，正常退出当前 Codex，让 Bridge 自动打开受管桌面。新安装仍使用自己的空账本；已有安装复用原账本。

在入口群 @ 机器人发送 `/topic new <projectKey> <名称>`。项目标识来自自己的 `topics.json`；新装向导默认使用 `main`。新话题先持久化其绑定账本，再进入 `active`，原绑定不得删除或改指另一条对话。创建回执不明时使用 `/topic resume <原消息编号>`；不会重复创建结果不明的资源。v0.9.1 对已保存对话 ID、停在初始化阶段的请求，先只读核验同一对话的项目、目录和持久完成轮次，通过后接续建群；没有完成证明时仍暂停，不重新提交初始化输入。

完整模式的 `listener.ready.json` 标记为 `scope: "registered-topics"`，包含匹配的入口群及 `allowTopicCreation: true`；此模式下 `enabledChatIds: []` 表示登记绑定范围，不能在默认单群模式中把空数组当作完整范围。各群的 `/status`、`/steer`、`/stop`、`/result`、`/reconcile` 和审批仍归属于该群自己的原生对话。新话题的本地文字记录位于对应项目的 `.lark-chatgpt-bridge` 中。

依次验证入口群、旧话题群、新话题及跨项目路由，确认唯一新消息回执，再验证需要的控制与审批操作。正常退出后再次启动，确认新增绑定仍可接续，最后迁移唯一登录入口。完整模式保留相同的原生空闲、队列、工具目录、进程身份和健康检查。

## 单聊主控配置 v0.10.0

在新的配置副本中增加 `topics.json` 的 `directControl`，保留原有 `entryChatId`、`existing` 和注册表。以下均为占位示例，请替换为已核验的真实资源：

```json
{
  "directControl": {
    "chatId": "oc_ownerdm",
    "projectKey": "main",
    "threadId": "verified-control-thread",
    "stateFile": "D:\\QIUBridge\\state\\direct-control-ledger.json"
  }
}
```

为主控准备单独、持久化完成初始化的 Codex 项目对话，不得与入口群或任何话题复用同一对话。将它加入 `host.json` 对应项目的 `toolBindings`，核对项目 ID、根目录和完整工具接线。不要填入当前负责安装且仍在运行的对话。

首次新增的主控账本为 UTF-8 JSON，结构与已有账本相同：`version: 1`、准确的 `binding`（appId、chatId、ownerOpenId、projectId、projectRoot、threadId）及空 `messages` 数组。仅为新绑定创建空账本，不覆盖或清空旧账本。然后重新准备新 stage 和 service，按既有流程校验、切换和验收。

监听采用 SDK 的所有者私聊允许名单，并再次核对精确单聊 ID、消息类型和所有者。就绪标记包含匹配的 `directControlChatId`；单聊同样纳入账本、审批、原生绑定、健康及退出核对。群聊继续沿用原来的 @ 要求。只有启用话题创建时，单聊才允许 `/topic new` 和 `/topic resume`；不会为陌生私聊自动建会话。

验收普通单聊文字、`/status`、`/result`、单聊创建话题、话题群 @ 收发及原入口群，确认结果进入各自对话；需要的停止、追加及审批也应在单聊单独验证。新建话题回复和 `/topic list` 提供群入口，不自动复制上下文或跨群执行。

## 启动与退出

通过 Windows Startup 中唯一的 `QIU New Bridge` 启动。登录时由 Bridge 负责打开受管 Codex；请关闭 Codex 自己的登录启动，避免顺序冲突。不要同时使用旧 CLI 消费者。

当前普通 Codex 仍在时，Bridge 会等你正常退出，最长十分钟；不会强关正在使用的窗口。保存工作、确认任务与审批已结束后退出，等待它自动打开。正常关闭受管桌面后，消息渠道也保持关闭；下次从同一入口启动，不必重配群或对话。

**自动打开窗口不等于消息渠道已经就绪。** Bridge 随后核对共享后台和已加载任务，再启动消息监听。正常桌面任务活动会等待结束并重新检查，所有复查共用最多十分钟预算；审批、队列、身份变化或未知失败仍阻断。请先等待实际就绪，不以固定静置时长代替检查。使用下方只读状态命令核对 `running`、监听连接和独立记录后再开始使用。

若启动被活动任务或其他检查挡住，先保留该次结果并核验清理，查明原因后准备新的运行；不要反复点击入口、删除失败指针或跳过空闲检查。负责安装的助手应在发起退出步骤前完成准备，并等待独立记录，不在检查期间启动自己的桌面任务。

正式服务模式没有验收窗口的 45 分钟自动截止。broker 仍受持续租约和健康核对约束；它不是脱离用户桌面的系统后台，也不保证电脑睡眠、断电后无条件恢复。

## 群内使用

周报、会议行动项、客户准备、数据小结和多话题的完整提问示例见[办公使用指南](office-workflows.zh.md)（[English](office-workflows.en.md)）。

仅配置的所有者、已启用群和支持的文字消息进入原对话。默认需要 @ 机器人。命令以当前群内 `/help` 返回为准，核心命令包括：

| 命令 | 用途 |
|---|---|
| `/status` | 查看当前桥接与对话状态 |
| `/steer <补充内容>` | 向当前轮次补充指令 |
| `/stop` | 请求停止当前原生轮次 |
| `/result <messageId>` | 明确取回指定消息已保存的结果 |

审批卡片只对匹配的群、所有者和原生待审批请求生效。不要把普通文字“同意”当成所有操作的授权。默认单群部署关闭 `/topic new` 等资源创建；完整模式按上文显式启用。

原生中断后，自动队列调度可能保持暂停。v0.9.4 会核对已接收的原队列编号、客户端消息和原文，只在其仍为队首且对话空闲时接续；开始前重新检查连接和健康状态。它不会越过更早的桌面请求，也不会把原文再次加入队列。启动响应不明确时先按原消息核对，不盲目重试。

## 查看状态与主动停止

从安装输出保存的服务目录读取活动计划，不凭旧截图或历史 PID 判断：

```powershell
$service = 'D:\QIUBridge\service'
$run = Get-Content -Raw -Encoding UTF8 (Join-Path $service 'active-run.json') | ConvertFrom-Json
node bin/lark-chatgpt-runtime-supervisor.mjs --status $run.planFile $run.planSha256
```

`supervisor.json` 的 `running` 表示该次消息服务已运行，仍需结合监听就绪、真实新消息和回执核对。`closed` 表示正常退出并已核验，`restored` 表示恢复普通桌面且消息暂停，`blocked` 表示证据或清理尚有问题。

需要主动停止时：

```powershell
node bin/lark-chatgpt-runtime-supervisor.mjs --stop $run.planFile $run.planSha256
```

停止请求返回不等于退出已完成；等待该运行的 `runtime.result.json`，确认自有角色退出及普通桌面恢复。不要删除活锁或用任务管理器杀掉不确定归属的进程。

`runtime.result.json` 中历史固定字段 `productionReady=false` 不是发布开关，不修改它来表示上线。判断依据是明确的版本、范围、监督状态、工具与消息回执、独立清理证据；已终止的运行也不会因为仓库发布而重新成为在线状态。

## 故障处理

v0.10.0 的登录入口固定使用 Windows PowerShell 自带模块，避免继承其他 PowerShell 环境时找不到校验命令。每次入口执行在服务目录的 `startup/*.jsonl` 记录阶段、固定错误代码和错误摘要；清单验证前的失败留在当前用户临时目录 `QIUBridgeStartup`。启动失败显示短暂提示，不记录原始错误、凭据或消息。`requested` 只表示已请求创建工作进程，不能当成渠道 `running`。

桌面窗口打开后，监听接入仍需完成原生空闲核对。此时有正常桌面任务活动会等待结束后重新核对，共用最多十分钟预算；不会因此立即把桌面恢复成普通模式。`shared-admission-wait.json` 记录等待或已完成状态，原始忙碌观察保留在独立文件。每轮复查仍检查同一进程、工具、锁及退役定义。不要用“窗口已打开两分钟”代替真正的监听就绪；审批、队列、未知错误及身份变化也不会被当作普通忙碌放行。

锁检查按启动阶段执行：监听尚未创建时，主机连接锁必须已持有，话题注册表锁必须空闲；监听启动后才要求两把锁都已持有。启动前遇到其他进程持有话题锁会拒绝接入，不能把外来锁当作自己的监听已启动。

上次因 `runtime_health_failed` 或 `shared_admission_busy_timeout` 暂停后，若记录证明普通桌面恢复完整、没有清理错误，并且原运行和结果相符，新的登录或手动入口可重新核对进程、旧任务退役状态、原消息账本及审批，进入全新的冷启动。原日志不改写，新运行保存 `previous-run-reentry.json`。该流程不会重新执行旧消息，也不会在你正常退出桌面后自行拉起；同一次开机中未完成的运行、清理不明、启动结果不明和其他错误继续阻断。

v0.10.0 起，每次服务入口保存绑定到本次计划和版本的 `service-boot.json`，并在运行指针中保存其 SHA-256。下次登录或手动启动时，如果原生证据确认同一台电脑已重新开机、旧记录均早于本次开机，即使上次清理失败或来不及写结束记录，也可以重新检查准入。仍须确认旧渠道进程已不存在、旧任务退役定义相同、所有账本与审批可安全接入，随后重新验证桌面、工具和原生任务空闲。任何不确定的已提交任务都阻止接入，不能用空账本绕过。该路径只建立新运行，保留旧故障和清理失败记录，不声称上次已正常退出，也不重发旧消息。

没有开机证据的旧版本、证据损坏、来源不符、开机时间未改变（包括睡眠唤醒）、旧进程仍在或账本不确定时继续暂停，需独立核对。升级不能只替换文件；需准备并核验新部署、迁移唯一登录入口，再在本机验证重启和真实收发。Windows 快速启动若未产生新的原生开机时间，不适用此恢复路径。

新版本将 `-32600` 记录为请求被拒绝，不单凭此代码断言接口不支持。只有未绑定、两次均空闲的临时对话，且队列第一页返回匹配本对话的精确原生“不支持队列”错误，才可确认该对话不可排队；绑定或持久对话、后续分页错误和其他拒绝均不适用。成功检查会记录相关临时对话 ID；失败诊断保留方法、对话 ID、检查轮次和错误 SHA，不记录原始错误或正文。

短暂飞书断线时，监听器保留原连接并启用 SDK 保活，监督程序最多等待三分钟。等待期间暂停新模型提交；连接连续稳定五秒后才恢复。等待时间从首次断线计起，反复抖动不会续期。身份、完整工具目录、锁、租约和群范围仍持续核对，任何异常都会暂停；不会重放已提交任务或盲目重发失败回执。

`listener.connection.json` 保留最近连接状态、最多 32 次状态变化和错误摘要 SHA-256，关闭后仍保留；`runtime-health.listener-recovery.json` 记录有界恢复结果。它们不保存原始异常、凭据或消息正文。原有 `runtime-health.failure.json` 仍记录首次失败。历史版本没有具体连接状态时，不应从一次“未连接”推断其底层网络原因。

1. 保存该次运行目录和原消息账本，在本机核对首次失败标签、计划/运行编号及完整进程身份。
2. 确认消息渠道是否已暂停，普通桌面是否恢复；不要把 `restored` 当成监听已重启。
3. `uncertain` 表示请求可能已执行，先回读原对话、原消息 ID、轮次和回执；不得直接重发、清账或新建空账本。
4. 原始请求结果已保存时，可显式 `/result <messageId>` 取回；新取回回执不伪填原发送回执。
5. 只有完成独立清理和原状态核对后，才创建新的唯一运行。启动入口对失败或不明确的上次运行会拒绝重试，这是保护行为。

不要为排障关闭完整性校验、安全软件或单位策略。公开问题反馈只附脱敏标签、版本及复现步骤。

历史请求可以在完整、唯一的原生轮次证据支持下核对终态。`reconciliation` 保存核对时间、证据摘要、原状态及核对出的原生结果，原错误通知和原回执保持原样；`/result` 显式返回核对出的答案。此类核对不能重新执行原输入，也不能把旧错误通知回执当作新答案已发送的证明。

## 更新或迁移

- 备份程序、配置、服务清单、账本、注册表、审批记录及凭据服务的引用；密钥仍留原加密库。
- 停止现有消费者并核验清理。保留历史不确定和失败记录，不重放消息。
- 新版安装在独立固定目录，重新构建程序 SHA 与部署清单，复用实际绑定和账本，而非运行新装向导重置它们。
- 按当前机器重新核对桌面包版本、自带 Codex 二进制、完整工具目录与原生项目/对话归属。升级不匹配时停止，不放宽门禁。
- 完成单群收发、桌面接续、退出保持关闭及重入核对后，才将唯一 Startup 入口切到新版本；保留原入口备份，但不要把备份放在实际 Startup 中。

安全软件恢复的 `QIU New Bridge(1).lnk` 也会成为登录入口。保留一个已验证入口，备份放到其他目录。快捷方式工具拒绝覆盖另一个所有者或版本的同名入口，迁移需明确核对目标与清单 SHA。

首版 Windows 运行核心的现场验收在原单群范围关闭；公开发布不自动扩大到其他群，也不把他人电脑计作已验证安装。
